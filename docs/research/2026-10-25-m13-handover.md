originals unchanged (0/54) and took a verified backup (`backups/m13live1-original-20261025T093214Z`,

a fresh trial". No PPSSPP process was spawned (`spawned_pids: []`) and no game input was sent.

Cause, measured: in m13live2 the backup receipt was issued at 09:42:29, preparation finished at 09:43:01, and the
launch refused at 09:43:33, about 64 s after the receipt. The limit is `BackupGate.freshness_seconds = 60`. Hashing
is fast (0.7 s for the originals; each validation inventory about 1.7 s; process guard 1.5 s). The slow call is
`WindowsInspector.listeners` (`Get-NetTCPConnection -State Listen`), which takes 11.6 s and once more than
15 s (it timed out). `netstat -ano -p TCP` answers in 0.1 s. The launch calls the listener check more than once
inside the freshness window. This is a Windows-side slowdown, new since the m12 runs this afternoon.

Options (user decision): (1) listener check via `netstat -ano -p TCP` parsing (fail-closed, tests first);
(2) restart Windows or wait, then retry unchanged; (3) a longer freshness window. Recommended: (1).

User chose (1). Done red-first: `WindowsInspector.listeners` (`src/psp_buddy/launch.py`) runs
`netstat -ano -p TCP` and `-p TCPv6`; `-p TCP` alone shows only IPv4, which would miss a `[::]` listener. It
fails closed on a failed run, a TCP row that does not parse, or no LISTENING row at all (a localized state).
The 15 s timeout is kept. Tests: `tests/unit/test_windows_inspector.py` (8). Live: 0.16 s. Checks: pytest 1602 / 1
skipped, helper + driver 196, node 8, ruff, strict mypy.
