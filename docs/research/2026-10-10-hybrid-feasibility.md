# Hybrid runner feasibility

Current status: portable v1.20.4 loaded the tested state with matching HP/EN fields. The user confirmed direct API cursor movement and normal in-game save loading. Full memory profiles, reliable v1.20.4 capture, and checkpoint automation remain unverified. The sections below record chronological findings; earlier limitations are superseded only where later evidence explicitly resolves them.

## Installed PPSSPP v1.9.3

The official v1.9.3 source registers these useful WebSocket debugger commands:

- `version`, `game.status`: emulator version and game status.
- `cpu.evaluate`: evaluate expressions; the MIPS expression evaluator supports 1-, 2-, and 4-byte memory reads.
- `cpu.stepping`, `cpu.resume`, `cpu.status`: execution control.
- `gpu.buffer.screenshot`: screenshots, including PNG data URIs.

This version's debugger subscribers do not register button-input or save-state commands, or the newer bulk `memory.read` command. Proposed integration: use the debugger for observations and screenshots, and Windows input for game controls and PPSSPP save/load controls. Verify input behavior and save completion in a protected runtime trial before adopting this design.

Remote debugging is disabled in the normal configuration. The protected trial enabled it in a separate ignored trial configuration, using the emulator's `--config` and `--controlconfig` options. An emulator upgrade is not yet justified by these findings.

## Game data and recognition

The local patch changelog identifies v0.8 and warns of untranslated text, alignment problems, and compressed menu labels. Use local menu recognition as confirmation, rather than relying exclusively on OCR.

No robot, pilot, or battle memory addresses have been validated against this patched ISO. The next investigation must correlate debugger memory values with visible unit statistics and verify them across state reloads. Required observations include HP/max HP, SP and Trust availability, repair capability, positions, affiliation, action availability, turn phase, attack prediction, defeat, and map completion.

Disappearance from the map alone is insufficient evidence of defeat: scripted exits and other legitimate transitions need to be distinguished. Unknown or contradictory observations must cause handover.

## Agreed MVP behavior

- One map, starting from an existing save state.
- Below 70% HP, prefer Repair if a capable ally can reach and repair this turn; otherwise use Trust if available. If neither is available, avoid attacking and move away from enemies.
- Enemy response priority: defend when enemy hit rate is greater than 80%; otherwise evade below 50% HP; otherwise counterattack when legal.
- One working save-state slot for the stage. Overwrite after all allies finish their actions and before ending the turn.
- After allied defeat, reload the latest checkpoint and change enemy-phase responses. Allied movement and healing cannot be redone from this checkpoint.
- Maximum three reload-and-retry operations per checkpoint. Reset after a successful enemy phase. Hand over when the retry budget is exhausted or the map finishes.
- Run tactics locally with deterministic rules; avoid model calls per action or per frame.
- Before every emulator trial, create and SHA-256-verify a fresh backup of complete SAVEDATA and PPSSPP_STATE directories according to AGENTS.md.

Retries may reproduce identical outcomes if responses and game randomness remain unchanged. Alternative responses must be deliberately chosen and recorded, not generated by repeatedly asking a model.

## Input backend investigation

The v1.9.3 Windows source uses Raw Input (`WM_INPUT` / `GetRawInputData`) to forward keyboard state through `NativeKey`. Menu activity can suppress forwarding. The absence of cursor movement does not establish exactly where automated input was lost: event delivery, focus/menu state, timing, and game processing have not been separately instrumented. No confirmed root cause is claimed. Changing fullscreen did not resolve native capture.

The official current stable release queried during investigation was v1.20.4. Its versioned debugger source registers `input.buttons.send`, `input.buttons.press`, and `input.analog.send`. Button commands call the emulator's controller state directly. A timed press takes a button name and duration in frames; its response arrives after release. This is a suitable alternative to investigate because it bypasses the Windows keyboard path. It also has `memory.read` for bulk reads, removing the need for process-memory access during ordinary observation.

The official Windows x64 portable archive was downloaded and verified against the release's SHA-256 digest in the ignored private trial area. The executable reports v1.20.4. It has not been run or installed. Recommended next trial: keep the existing installation, make a fresh verified backup, create a separate portable memory stick using copied saves/settings, load a copied slot-2 state, and compare before/after screenshots for a single direct API cursor press. Verify state compatibility and release all injected buttons before handover. Saving through the emulator's own interface still needs a separate verified mechanism; the input API alone does not establish save-state automation.

## Portable v1.20.4 compatibility trial

The user approved testing the newer version if saved data is compatible. A fresh backup of all 44 original saves/settings passed SHA-256 verification. A separate writable portable memory stick was populated with verified copies; the installed emulator and original Documents memory stick were not used for writes.

The portable executable returned v1.20.4, loaded copied slot 2, and identified ULJS00460 version 1.01. All five checked fields matched the old version: Gundam 00 HP 5000 and EN 121, Shenlong HP 4616, candidate maximum HP 5300, and EN 7. This establishes compatibility of this specific state and the checked game data. Normal in-game BIN loading and other states are not yet tested.

Both `gpu.buffer.screenshot` and `gpu.buffer.renderColor` returned `Could not download output` under the inherited Direct3D11 backend; each brief pause was followed by resume in cleanup. Native Windows capture also timed out. The user was asked whether the battle map is visible or the game area is blank; graphics changes should follow that observation rather than assume a cause.

`input.buttons.press` with right and a duration of three frames completed successfully. `input.buttons.send` explicitly released right afterward; `cpu.status` confirmed the game was running. The command path is verified, but cursor movement has not yet been visually confirmed. Do not promote acknowledgment alone to verification of game behavior.

Subsequent user observations confirmed that the new emulator window displayed the game, the injected press moved the cursor right exactly one tile, and normal in-game saves could be loaded through the game menu. This corroborates direct input and compatibility of the tested normal save. Automated recognition and save-state creation/reload are separate outstanding checks.
